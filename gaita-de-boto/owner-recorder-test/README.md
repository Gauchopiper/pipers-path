## Work Handover 10: pending recording recovery

`pending-store.js` stores one unconfirmed recording per pupil capability. Audio and immutable metadata (Session ID, MIME type, start/end and target) are AES-GCM encrypted together. A non-extractable key is derived in memory with HKDF from the existing private link and pupil ID; neither credentials nor plaintext identity/audio are written to IndexedDB. The lookup slot is a SHA-256 digest. A different pupil/key cannot decrypt it. Someone possessing the same private link, malicious same-origin code, or a compromised browser profile is outside this isolation guarantee. Existing Google Owner authentication and bridge guards are unchanged.

No automatic expiry: retain until authoritative server confirmation or explicit user-confirmed deletion. A pending recording blocks starting another. Atomic add prevents another tab overwriting a pending item; Web Locks serialize same-pupil saves where supported, with server idempotency retained. Browser quota/private mode/eviction can still remove or prevent storage. Persistence is requested but not assumed granted. Failure displays a warning and keeps in-memory playback/download; failed recovery initialization blocks new recording to avoid overwriting unknown pending work.

Protection is committed AFTER Stop, before upload. Abrupt termination during recording or before the local-protection confirmation can lose audio. This does not cache the application shell or Google authentication: reopening may require connectivity even though stored audio survives. Key regeneration or clearing browser/site data can make pending audio unrecoverable; do not rotate keys while pending recordings exist. Download remains the fallback.

Tests: `node pending-store.test.cjs` uses real WebCrypto with simulated IndexedDB transactions. `node recovery-flow.test.cjs` tests the actual frontend helpers with simulated storage/network. Existing `node reliability.test.cjs` and `node verify.cjs` remain. Real HTTP cloud preview shows the expected local-protection-unavailable guard because WebCrypto requires a secure context. Real HTTPS IndexedDB close/reopen, browser restart and actual network interruptions remain device tests; no live recovery pass is claimed.
